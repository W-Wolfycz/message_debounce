# 消息防抖 (message_debounce)

按用户维度做**纯时间防抖**：同一用户在防抖窗口内再次发消息时，上一条消息的
待发送回复会被静默取消，只回复窗口内最新一条；被取消的前文会**合并进最终请求
的 prompt**，让 LLM 看到完整语境。

例如窗口为 3 秒，用户 1 秒内连发「A」「B」「C」三条消息，则 A、B 的待发送回复
均被取消，最终只有一次请求，其 prompt 为「A\nB\nC」的合并文本。

## 工作原理

AstrBot 消息流转中插件的拦截点（按阶段顺序）：

1. **消息到达**（ProcessStage 的 `event_message_type` Handler）：记录**唤醒 bot 的
   真实消息**的到达时间戳并缓冲其文本。只记录、不拦截、不改写事件原文——
   chat_memory 等插件仍按原始 `message_str` 逐条归档；未唤醒 bot 的群聊消息
   （没 @、没唤醒前缀）、命令消息（指令 Handler 直接回复、默认不走 LLM）、
   bot 自身回显、通知 / 请求类事件（如 NapCat 的「正在输入」`input_status`）
   都不参与防抖；
2. **LLM 请求发起前**（`on_llm_request`，两道）：
   - **最早**（priority 100_000）：若该消息已被更新的消息取代，`stop_event()`
     中止本次 LLM 请求；若自己是窗口内最后一条且带着被取消的前文，等待剩余
     窗口静默（期间新消息到达立即唤醒并取而代之），然后把缓冲文本合并进
     `ProviderRequest.prompt`；
   - **最晚**（priority -10_000_000）：链上耗时插件（如 CM/LM 查询）运行期间
     新消息到达时，在请求真正发出前再查一次取消标记，命中则中止，省掉一次
     LLM 调用；
3. **LLM 响应刚返回**（`on_llm_response`）：若生成期间被新消息取代，
   `stop_event()` 中止——非流式路径下核心会跳过发送与历史保存，取消干净，
   不留「幽灵回复」；未命中则回复注定会发出，此刻关闭该串缓冲——已回复的
   消息不再作为后续合并的前文，期间已有新消息到达则保留缓冲给下一位载体，
   连发链照常合并。

已发送或已开始流式输出的回复**不追回**（不在 `on_decorating_result` 拦截）。

> 首条消息立即发起请求，只有**带前文的载体**才等待窗口静默。因此若某条的回复
> 已经发出，窗口内随后到达的消息不会与它合并（避免重复合并已回复文本），
> 各自回复。

### 合并与插件链协作

- 合并只发生在 `ProviderRequest.prompt` 层，**事件原文（`message_str`）不变**，
  因此 chat_memory 的逐条审计归档完全不受影响：每条消息仍按原文、时间戳、
  message_id、引用关系独立落库；
- 合并发生时设置事件 extra `message_debounce_merge`（`{"count": n,
  "window": w}`），`on_llm_request` 之后的所有插件 hook（含 chat_memory）
  均可通过 `event.get_extra` 感知这是一次合并请求；
- 合并时通过 `extra_user_content_parts` 向 LLM 追加一条合并说明（`TextPart` +
  `mark_as_temp()`，不写入会话历史）。

用户维度键 = 平台实例 ID + 会话 ID + 发送者 ID，各平台实例、群聊/私聊、用户之间
完全隔离。

## 配置

| 配置项 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `window` | float | `0` | 防抖窗口（秒）；`0` = 关闭插件（默认关闭，安装后需手动给窗口值） |
| `session_blacklist` | list | `[]` | 停用会话黑名单：群聊 `G:<群号>`、私聊 `F:<用户号>`（必须带前缀，群号与用户号可能同号）；列表内会话不启用防抖，**留空 = 全部启用** |
| `log_with_bot_id` | bool | `false` | 日志前缀附加平台实例：`[message_debounce][platform:<平台实例>]`，多 Bot 实例环境可区分来源 |

## 安装

AstrBot 插件市场搜索「消息防抖」安装，或克隆本仓库到
`data/plugins/message_debounce/` 后在 WebUI 插件管理中重载。无第三方依赖。

## 局限与说明

- 若上一条消息的 LLM 回复**已开始流式输出**，已发出的部分无法撤回（流式块在
  `on_llm_response` 之前已直接发出）；本插件尽力在请求发起前拦截。
- 回复在 `on_llm_response` 之后已经发出的不追回（按设计不在
  `on_decorating_result` 拦截）。
- 非流式路径在 `on_llm_response` 中止是干净的：不发送、不写入会话历史；但其他
  插件的 `on_agent_done` 观察者仍可能看到这次被中止的回复。
- 被取消的轮次在 chat_memory 里是「只有 user、没有 bot 回复」的普通用户消息
  （llm_status 停在默认值），归档内容完整但不与合并回复配对；如需配对可让
  chat_memory 读 `message_debounce_merge` extra 做适配（插件侧另批）。
- 开启 `buffer_intermediate_messages`（缓冲中间消息）时，工具循环中已缓冲的
  中间消息可能仍会被合并发出（核心在该模式下合并发送前不检查停止标记）。
- 仅按时间窗口判断，不识别句子是否完整；需要语义级防抖可参考
  `astrbot_plugin_debounce` 等插件。
- 只有**默认会进入 LLM 的唤醒消息**参与防抖：群聊需 @ 或唤醒前缀，私聊默认可
  直接唤醒；未唤醒的消息、命令消息都不记录、不缓冲，也不会取消上一条待发送
  回复。黑名单（`session_blacklist`）内的会话整体不启用。
- 只有带前文的载体才等待窗口静默：单条消息立即回复（无窗口延迟）；若上一条的
  回复已经发出，窗口内随后到达的消息会另起一串、各自回复。
